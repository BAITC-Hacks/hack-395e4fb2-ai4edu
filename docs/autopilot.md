# AI-автопилот: цель пользователя → проверенный план

Автопилот самостоятельно подбирает пять городских мероприятий, рассчитывает их
последствия, готовит объяснение и проверяет его. Пользователь пишет цель обычным
языком; предварительно выбирать пять мероприятий не требуется. Числа, ограничения
и сравнение вариантов всегда проверяет Go-движок на синтетическом датасете проекта.

## Что делает каждая роль

Три роли OpenAI работают в одном управляемом Go-координаторе:

| Роль | Вход | Результат | Кто проверяет |
|---|---|---|---|
| `master` — мастер | Неизменный текст цели и полный сценарий города; при исправлении — предыдущие `brief` и рецензия | `Brief`: формальная цель, ограничения, краткое описание или вопрос для уточнения | Go проверяет формат и поддерживаемые ограничения; рецензент проверяет смысл |
| `planner` — планировщик | Формальная цель, до пяти рассчитанных кандидатов, значения показателей, определения мер, предыдущая рецензия | Индекс выбранного кандидата и обоснование | Go проверяет индекс, допустимость и равенство лучшему результату по цели и Score |
| `reviewer` — рецензент | Исходная цель, формальная цель, лучший и выбранный результаты, обоснование, контекст мер | `approved`, замечания `feedback`, риски `tradeoffs`, адресат исправления `revision_target` | Координатор принимает положительную рецензию с `revision_target=none`, непустым обоснованием и повторной проверкой ограничений |

Поиск выполняется локальной функцией `optimizer.Search`. Она перебирает допустимые
варианты, вызывает единственный движок `simulation.Simulate`, проверяет ограничения
и возвращает до пяти лучших результатов. Этот поиск не расходует API-токены.
Планировщик выбирает серверный кандидат по индексу: модель не может подменить
решения, стоимость или рассчитанные показатели в результате.

```text
Исходная цель → проверка явно указанного бюджета → мастер → проверка brief в Go
  → полный поиск Go → планировщик → рецензент
  несовпадение явно указанного бюджета и brief → замечание Go → мастер
  рецензия: master  → тот же исходный запрос + прежний brief + замечания → мастер
  рецензия: planner → замечания → планировщик с теми же проверенными кандидатами
  рецензия: none и approved=true → итоговая проверка Go → completed
```

Если неверно понята цель или потеряно ограничение пользователя, рецензент возвращает
`revision_target=master`. Координатор снова вызывает мастера с **исходным текстом
цели**, прежним `brief` и замечаниями, затем запускает поиск по исправленной
формальной цели. Исходный запрос пользователя не меняется; исправляется его перевод
в поддерживаемые поля. Неподдерживаемые требования приводят к `needs_clarification`.

Дополнительно Go проверяет явно записанное числовое ограничение бюджета для
поддерживаемых русских и английских формулировок. Если мастер заменил распознанное
число другим, координатор **до поиска** создаёт замечание с адресатом `master`
и событие `explicit_budget_correction`. Повторный вызов мастера получает исходный
запрос и это замечание; он расходует следующую общую итерацию. Рецензента ждать
для обнаружения такого расхождения не требуется. Недопустимые или неоднозначные
распознанные значения бюджета приводят к `needs_clarification` до обращения к API.

Это ограниченная проверка числового условия, а не универсальное понимание текста.
Примеры распознаваемых записей: «при бюджете не больше 95», «бюджет: 90»,
«бюджет до 80», `budget at most 95`, `budget <=95`. Повтор одного и того же лимита
допускается; разные лимиты требуют уточнения. Дроби, диапазоны и числовые значения
вне 1–100 не превращаются в допустимый лимит. Посторонние числа в тексте не считаются
бюджетом; «не меньше 95» и числа словами не интерпретируются как верхний предел.
Неподдерживаемые обороты, другие цели и ограничения по-прежнему требуют
интерпретации и рецензии LLM. Go не гарантирует, что произвольное пожелание было
полностью распознано; исходный запрос и `brief` доступны для сравнения.

Перед повторной интерпретацией очищаются прежние `brief`, `result`, `explanation`,
`review`, `optimality` и статистика поиска. Если исправление или новый поиск не
завершится успешно, результат по прежним ограничениям не выдаётся за актуальный.

Если цель понята правильно, но объяснение или выбор требуют исправления, адресат —
`planner`. Он получает замечания и те же рассчитанные кандидаты. Одобрение требует
`approved=true` и `revision_target=none`; при отказе рецензент выбирает `master` или
`planner`. Повторение уже отклонённого предложения без изменений останавливает
запуск со статусом `needs_review`.

Возвраты к мастеру и планировщику используют **общий** `AUTOPILOT_MAX_ITERATIONS`.
Исправление мастером выполняется внутри следующей доступной итерации, а не запускает
новый неограниченный цикл. Общие лимиты времени и расходов продолжают действовать.

В новом автопилоте все три роли используют OpenAI. NVIDIA для него не требуется.
Отдельный существующий `/api/advise` сохраняет прежнюю механику: пользователь
передаёт пять решений, OpenAI проверяет до двух альтернатив инструментом
`simulate_scenario`, а NVIDIA при настройке добавляет рецензию. Это разные сценарии
работы; подробности прежнего советника — в [ai-integration.md](ai-integration.md).

## Поддерживаемые цели и ограничения

| Поле `Brief.goal` | Допустимые значения и смысл |
|---|---|
| `objective` | `score`: максимальный городской Score; `weakest_district`: максимальный Score самого слабого района; `focus_district`: максимальный Score указанного района; `critical_first`: прежде всего минимальное число критических показателей |
| `focus_district` | Для `focus_district` — один из `esil`, `almaty`, `saryarka`, `baikonur`, `nura`; для остальных целей — пустая строка |
| `budget_limit` | Целое число от 1 до 100 условных единиц. Это ограничение расходов внутри симулятора, а не деньги API |
| `max_critical` | `null`, если дополнительного ограничения нет; иначе целое число от 0 до 50 |
| `protect_districts` | Уникальные ID районов, чей суммарный районный Score после мер должен быть не ниже исходного Score до любых мер |

Критическое значение — пара «район × показатель» со значением **строго ниже 40**.
Защита районного Score не гарантирует, что каждый отдельный показатель района
останется прежним. Например, повышение безопасности может компенсировать снижение
транспортного показателя в суммарном Score.

При равенстве основной цели поиск предпочитает больший официальный городской
Score; окончательное равенство разрешается стабильным порядком решений.
Планировщик должен выбирать первый кандидат либо численно равный ему по основной
цели **и** итоговому Score. Выбор худшего варианта отправляется на исправление.

Примеры целей:

- «Максимизируй городской Score при бюджете не больше 90».
- «Максимизируй Score Нуры, не снижая суммарный Score остальных районов».
- «Сначала минимизируй число критических показателей, уложись в 100».

Пустая цель по инструкции мастеру означает максимизацию городского Score,
бюджет 100 и отсутствие дополнительных ограничений.

Если цель неоднозначна или содержит неподдерживаемое условие, мастер должен
запросить уточнение. Например, «не ухудшай ни одного отдельного показателя» нельзя
молча заменить защитой районного Score. Пользователь уточняет текст и создаёт
новый запуск: продолжение старого запуска с дополнительным сообщением не реализовано.

## Что означает успешный результат

Статус `completed` выставляется, когда поиск завершён полностью, выбранный план
соответствует формальной цели и ограничениям, его ранг равен лучшему найденному,
а рецензент одобрил объяснение. Все численные результаты повторно рассчитаны Go.

Это подтверждает численный оптимум **в данной модели и для переведённой формальной
цели**. Go не доказывает, что модель безошибочно поняла свободный текст, и не
доказывает истинность каждого предложения AI-объяснения. Рецензент также может
ошибаться. В ответе доступны исходная цель, `brief`, расчёт и рецензия, чтобы
интерпретацию можно было проверить. Синтетические данные не подтверждают реальные
последствия городской политики.

`result` может присутствовать и при неуспешном завершении: это сохранённый
рассчитанный промежуточный план. Наличие этого поля само по себе не означает
`completed`, одобрение рецензента или выполнение всей задачи.

### Численное подтверждение оптимума: `optimality`

Необязательное поле `optimality` вычисляется Go из лучшего и выбранного результатов.
Оно относится только к **текущей формализованной цели, её ограничениям и фиксированному
каталогу**. Оно может присутствовать до окончания AI-рецензии: численная оптимальность
и успешное завершение всего запуска — разные проверки.

| Поле | Смысл |
|---|---|
| `proven` | Полный поиск завершён, выбранный вариант равен лучшему по основной цели и итоговому городскому Score |
| `objective` | Цель из текущего `brief.goal.objective` |
| `best_value` | Значение основной цели у лучшего найденного варианта |
| `selected_value` | Значение основной цели у выбранного варианта |
| `gap` | Для целей максимизации: `best_value − selected_value`; для `critical_first`: `selected_value − best_value` |
| `score_ceiling` | Присутствует только для `objective=score` после полного поиска; максимальный городской Score при этих ограничениях |

Для `score`, `weakest_district` и `focus_district` значения выражены в **баллах Score,
не процентах**. Для `critical_first` это число критических пар «район × показатель»:
меньше означает лучше. Нулевой `gap` сам по себе не доказывает оптимум: при равенстве
основной цели ещё сравнивается итоговый городской Score. Отменённый или неполный
поиск не даёт доказательства; некорректные данные или отрицательный направленный
разрыв не превращаются в подтверждение оптимальности.

Для текущего датасета и бюджета 100 максимальный городской Score равен
**57.236735 балла**; это контрольное значение полного поиска, а не 57.236735% и не
обещание улучшить реальный город на такой процент. При другой цели, ограничениях
или каталоге сравнение необходимо выполнить заново. `proven=true` не подтверждает
безошибочность перевода пожелания пользователя, текста LLM или самой модели города.

## Запуск и API

Настройте локальный `.env`, затем запустите сервер командой `make run`.
Ключ OpenAI остаётся на сервере; его не передают в запросах frontend.
Без `OPENAI_API_KEY` автопилот отключён, а остальные возможности симулятора
сохраняются согласно их собственной конфигурации.

### Создание запуска

```sh
curl -sS -i http://localhost:8080/api/autopilot \
  -H 'Content-Type: application/json' \
  --data-raw '{"goal":"Максимизируй городской Score при бюджете не больше 90"}'
```

Успех: **202 Accepted**, JSON-объект запуска и заголовок
`Location: /api/autopilot/<id>`. Начальный статус — `queued`. Текст цели ограничен
2000 Unicode-символами. Общий лимит тела запроса API — 64 KiB; неизвестные поля
и несколько JSON-объектов подряд отклоняются.

Создание запуска начинает фоновую задачу; закрытие HTTP-соединения или вкладки
само по себе не отменяет её. Повторный POST создаёт новый оплачиваемый запуск.
Для проверки состояния используйте GET по уже полученному ID.

### Получение состояния и отмена

Вместо `<id>` подставьте ID из ответа создания:

```sh
curl -sS 'http://localhost:8080/api/autopilot/<id>'
curl -sS -X POST 'http://localhost:8080/api/autopilot/<id>/cancel'
```

Оба маршрута возвращают **200** с текущим объектом запуска или **404**
`{"error":"autopilot_not_found"}` для неизвестного ID. Отмена уже завершённого
запуска возвращает его прежний результат. Отмена активного запуска не возвращает
стоимость уже отправленных запросов к модели.

| Ошибка создания | HTTP | Значение `error` |
|---|---:|---|
| OpenAI/автопилот не настроен | 503 | `autopilot_disabled` |
| Все слоты заняты | 429 | `autopilot_busy`; `Retry-After: 5` |
| Некорректная или слишком длинная цель | 400 | `invalid_goal` |
| Не удалось создать запуск | 500 | `autopilot_failed` |

Ошибки декодирования общего HTTP-слоя возвращаются отдельно в
`validation_errors`, как описано в [api.md](api.md).

### Поля ответа

| Поля | Содержание |
|---|---|
| `id`, `status`, `message` | Идентификатор, машинный статус и понятное сообщение |
| `goal`, `brief` | Исходный запрос и его формальная интерпретация; `brief` отсутствует до ответа мастера |
| `result` | Полный результат симулятора с пятью решениями, ценой, Score, районами до/после и эффектами; отсутствует до поиска |
| `explanation`, `review` | Обоснование выбранного плана и последняя рецензия; `review` может отсутствовать |
| `review.revision_target` | `none`: исправления не нужны; `planner`: исправить предложение/объяснение; `master`: исправить формализацию исходной цели |
| `optimality` | Необязательное численное подтверждение оптимума для текущей формальной цели; не заменяет `status=completed` |
| `events` | Публичные этапы: `agent`, `stage`, `message`, `iteration`, `at`; внутренние рассуждения моделей не возвращаются |
| `iterations` | Номер общей итерации, начиная с 1; включает исправление мастером, если оно потребовалось, затем планировщика/рецензента; до цикла — 0 |
| `evaluated`, `feasible`, `exhaustive` | Число проверенных после предварительного отсева вариантов, число удовлетворяющих ограничениям, завершённость полного поиска |
| `usage` | По одному элементу на выполненный вызов: `model`, `input_tokens`, `output_tokens`, `estimated_cost_usd`, `uncertain` |
| `estimated_cost_usd`, `budget_usd` | Учтённые расходы запуска и его локальный лимит в долларах |
| `created_at`, `updated_at` | Время создания и последнего изменения |

### Статусы

| `status` | Значение |
|---|---|
| `queued` | Запуск принят |
| `running` | Выполняется интерпретация, поиск, планирование или проверка |
| `completed` | Поиск и проверка завершены, план принят |
| `needs_clarification` | Цель требует уточнения; создайте новый запуск с уточнённым текстом |
| `infeasible` | Полный поиск подтвердил отсутствие допустимого плана при данных ограничениях |
| `needs_review` | Закончились итерации или повторилось отклонённое предложение; AI-проверка не завершена |
| `budget_exceeded` | Следующий запрос не помещается в лимит запуска или общего локального учёта |
| `unavailable` | Сбой, отказ, некорректный ответ модели или иная ошибка внешнего вызова/учёта |
| `cancelled` | Запуск отменён |
| `timeout` | Истёк общий срок запуска |
| `failed` | Внутренняя ошибка или результат поиска не прошёл проверку |

Только `queued` и `running` означают продолжающуюся работу. Остальные статусы
конечные; автоматически бесконечно перезапускать их не нужно.

## Лимиты и стоимость

По умолчанию работают не более двух запусков одновременно. Один запуск получает
180 секунд общего времени и до трёх общих итераций. Без исправления формальной цели
это максимум **семь API-вызовов**: один мастер плюс три пары планировщика/рецензента.
Если оба доступных повтора требуют мастера, верхняя граница — **девять вызовов**.
При `N` итерациях абсолютный предел — `3 × N`, то есть 15 при настройке пяти
итераций; общий срок остаётся 180 секунд. Начальный вызов мастера входит в первую
итерацию. Несовпадение явного бюджета и повторная интерпретация расходуют тот же
общий лимит; возврат к мастеру не сбрасывает счётчик.

Каждый вызов ограничен 25 секундами и 2048 выходными токенами. Раннее одобрение,
уточнение, ошибка, отсутствие вариантов, отмена, общий таймаут или бюджет могут
остановить процесс раньше; достижение максимального числа вызовов не гарантируется.

Перед вызовом резервируется консервативная стоимость: размер полного запроса
в байтах учитывается как число входных токенов, добавляется 1024 токена служебного
запаса и полный лимит выходных токенов. Максимальный сериализованный запрос
к провайдеру — 96 KiB. Перенаправления HTTP запрещены.

Если провайдер вернул `usage`, стоимость пересчитывается по фактическому числу
входных и выходных токенов и локальной таблице тарифов. Используется полный
входной тариф без скидки за кэширование. Это **оценка**, а не банковский счёт или
счёт провайдера. Если данные usage отсутствуют или запрос оборвался, `uncertain=true`
и в локальном учёте сохраняется вся зарезервированная сумма.

| Переменная | Значение по умолчанию | Назначение |
|---|---|---|
| `OPENAI_API_KEY` | пусто | Ключ API; отсутствие отключает автопилот |
| `OPENAI_MASTER_MODEL` | через общую настройку | Модель мастера |
| `OPENAI_PLANNER_MODEL` | через общую настройку | Модель планировщика |
| `OPENAI_REVIEWER_MODEL` | через общую настройку | Модель рецензента |
| `OPENAI_AGENT_MODEL` | `OPENAI_MODEL` | Общий резервный выбор модели для ролей |
| `OPENAI_MODEL` | `gpt-4.1-mini` | Последний общий резервный выбор |
| `AUTOPILOT_RUN_BUDGET_USD` | `0.10` | Лимит одного запуска; допустимо 0.001–5 |
| `AUTOPILOT_TOTAL_BUDGET_USD` | `50` | Общий предел локального учёта; допустимо 0.001–10000 |
| `AUTOPILOT_MAX_ITERATIONS` | `3` | Общий лимит итераций от 1 до 5, включая циклы с исправлением мастером |
| `AUTOPILOT_BUDGET_FILE` | `.autopilot/usage.json` | Файл учёта расходов, сохраняемый между перезапусками |
| `OPENAI_INPUT_USD_PER_MILLION` | пусто | Входной тариф для моделей без встроенной цены |
| `OPENAI_OUTPUT_USD_PER_MILLION` | пусто | Выходной тариф для моделей без встроенной цены |

Приоритет выбора модели для каждой роли: её индивидуальная переменная →
`OPENAI_AGENT_MODEL` → `OPENAI_MODEL` → `gpt-4.1-mini`. Для встроенных точных ID
`gpt-4.1-mini`, `gpt-6-sol`, `gpt-6-luna`, `gpt-6-astra` используются цены из
[адаптера](../internal/autopilot/openai.go). Для другого ID нужны обе переменные
тарифов: конечные положительные числа не больше 1000000 USD за миллион токенов.
Цены неизвестных версий и алиасов не угадываются. Пользовательские тарифы
применяются только к моделям без встроенной цены.

Дорогая модель может не поместиться в стандартный лимит одного запуска даже до
вызова API: проверьте резерв стоимости и осознанно задайте подходящий лимит.
После изменения `.env` перезапустите сервер.

Файл расходов рассчитан на **один серверный процесс**. Он хранит использованный
лимит и незавершённые резервы, чтобы сбой процесса не обнулял учёт. В Docker файл
нужно размещать в сохраняемом томе. Удаление файла сбрасывает местную историю
расходов, но не счёт провайдера.

Лимит `$50` относится только к этому локальному учёту автопилота. Он не читает
баланс OpenAI и не учитывает `/api/advise`, `/api/explain`, другие процессы или
другие приложения с тем же ключом. Контроль общего аккаунта остаётся отдельным.

## Хранение результатов и интерфейс

Запуски и события хранятся в памяти сервера: по умолчанию до 100 записей,
завершённые записи доступны один час. При заполнении хранилища старые завершённые
запуски могут удаляться раньше. После перезапуска сервера ID больше недоступны.
Файл `.autopilot/usage.json` сохраняет расходы, а не сами задачи.

Frontend показывает этапы работы ролей, результат и рецензию. Завершённые планы
сохраняются в истории браузера через `localStorage`; это локальное хранилище
пользователя, а не серверная база или общий аккаунт. Закрытие вкладки не отменяет
работу сервера; после возвращения frontend может продолжить опрос сохранённого
активного ID, пока он существует на сервере. Для остановки есть отдельная кнопка.

### Проверка с реальным API и браузером: 2026-09-23

Ниже — исторические проверки версии до добавления возврата рецензии мастеру и
поля `optimality`. Они подтверждают прежний успешный путь без исправления цели.
Эти три запуска не проверяли восстановление после намеренно неверной
формализации. Отдельная попытка такой проверки описана ниже.

Выполнены три запуска с реальным OpenAI API; дополнительно проверен браузерный
интерфейс. Цель:
максимальный городской Score при бюджете 100 и отсутствии критических показателей
после решений (`objective=score`, `budget_limit=100`, `max_critical=0`). Все три запуска
дошли до `completed` за примерно 34–35 секунд.

| Проверка | Первый запуск | Второй запуск | Третий запуск |
|---|---:|---:|---:|
| API-вызовы: мастер, планировщик, рецензент | 3 | 3 | 3 |
| Циклы планировщика/рецензента | 1 | 1 | 1 |
| Оценка стоимости по usage | ≈ $0.0069 | ≈ $0.0075 | ≈ $0.0077 |

Во всех трёх случаях полный Go-поиск проверил **694 395** вариантов после
предварительного отсева; **7 223** удовлетворяли дополнительным ограничениям.
Итоговый Score — **57.236735** (округлено для показа), стоимость плана — **98**
условных единиц, число критических показателей — **2 → 0**. Источник этих чисел —
рассчитанный `result`, а не текст модели. В браузере дополнительно проверены
восстановление опроса активного запуска после перезагрузки страницы и сохранение
завершённого результата в истории.

Обнаружено ограничение текстовой проверки: **во втором объяснении модель упомянула
парк, которого не было в выбранном плане, а рецензент одобрил текст**. Численные
результаты и список решений Go от этого не изменились. Успешный статус и отдельный
рецензент не гарантируют безошибочность свободного текста; действия следует
сверять с `result.decisions` и каталогом.

После добавления явных названий мер в `candidate_actions` и `selected_actions`
выполнен третий запуск продолжительностью 34 секунды. В его объяснении корректно
перечислены все пять действий: M14 и M2 для города; M3, M8 и M9 для Нуры.
Несуществующий парк больше не упоминался. Это подтверждает корректность названий
действий именно в данном ответе после изменения контекста. Отдельные технические
термины ещё встречаются в прозе; вероятностная генерация и одобрение рецензента
по-прежнему не дают гарантии безошибочности всех будущих объяснений.

### Проверка с намеренной ошибкой мастера

В первой платной проверке восстановления тест подменил начальный ответ мастера:
в исходной цели бюджет был ограничен **95**, а в `brief` было записано **100**.
Настоящий AI-рецензент не вернул ошибку мастеру и в итоге одобрил неверную
формализацию. **Эта проверка завершилась неуспешно**: одного разделения ролей и
инструкций модели оказалось недостаточно для соблюдения явного числового условия.

По результату добавлена описанная выше проверка бюджета в Go. Она обнаруживает
поддерживаемое явное числовое условие до поиска и отправляет расхождение мастеру
через `explicit_budget_correction`. Это исправление конкретного наблюдённого
случая, а не доказательство правильного понимания любых фраз.

**Повторная платная проверка исправленного пути прошла:** `TestLiveMasterCorrection`
завершился за **31.33 секунды**, использовав две общие итерации и три настоящих
API-вызова. Начальный неверный ответ мастера с бюджетом 100 был подменён тестом
локально и не обращался к API. Go обнаружил расхождение с исходным бюджетом 95
через `explicit_budget_correction`; настоящий мастер исправил формальную цель,
после чего выполнены полный поиск, настоящий планировщик и настоящий рецензент.

| Проверенный результат повторного теста | Значение |
|---|---:|
| `brief.goal.budget_limit` | 95 |
| `result.final_score` | 57.22554500 балла |
| `result.total_cost` | 91 |
| `result.critical_after` | 0 |
| `optimality.proven` | `true` |
| Статус | `completed` |
| Оценка стоимости по usage | $0.007739 |

Это подтверждает путь **Go-проверка → исправление реальным мастером → поиск →
планировщик и рецензент** в данном запуске. Ошибку обнаружил Go, а не LLM-рецензент;
первый неуспешный результат проверки не отменяется успешным повтором.

После обновления протокола также выполнен обычный браузерный запуск с
подтверждением оптимума: `completed`, Score **57.236735**, стоимость плана **98**,
критических показателей **0**, оценка API-расходов около **$0.0079**. Это отдельная
проверка текущей версии; три более ранних запуска выше сохранены как история.

Опциональный тест [live_test.go](../internal/autopilot/live_test.go) воспроизводит
эту ошибку и проверяет восстановление: начальный ответ мастера подменён локально,
а последующие мастер, планировщик и рецензент обращаются к настоящему OpenAI.
Проверяется событие Go, исправленный бюджет 95, допустимый план без критических
показателей, `completed` и подтверждение численного оптимума.

**Следующая команда расходует API-квоту.** `OPENAI_API_KEY` и нужные настройки
моделей должны быть заранее экспортированы в окружение; `go test` сам `.env`
не загружает. Тест запускается только при явном флаге:

```sh
RUN_PAID_AUTOPILOT_EVAL=1 go test ./internal/autopilot \
  -run '^TestLiveMasterCorrection$' -v -count=1 -timeout=210s
```

При обычном `go test` тест пропускается. Подменённый первый ответ мастера не
вызывает API; последующие реальные вызовы оплачиваются. Тест использует отдельный
лимит **$0.10** и журнал в памяти. Он **не входит** в постоянный общий журнал
запущенного сервера и не сохраняет накопленную сумму между запусками теста.
Повторная команда создаёт отдельную проверку с новым локальным лимитом.
