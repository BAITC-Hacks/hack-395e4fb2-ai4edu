# Web «Аким на 5 часов»

React + TypeScript + Vite. Проект находится в `web/`.
Контракт: [docs/api.md](../docs/api.md). Правила: [docs/scoring.md](../docs/scoring.md).
Интерфейс подключает симулятор, оптимизатор и автономный цикл AI-агентов Go-сервера.

## Запуск

Нужны Go 1.22+, make, Node.js 22.22.2+ (ветка 22) или 24.15+ и npm. Нижняя граница Node учитывает зависимости из package-lock.json. Текущие проверки выполнены на Node 24.19.0.

Терминал 1, в корне репозитория:

```sh
make run
```

Терминал 2:

```sh
cd web
npm ci
npm run dev
```

Откройте URL из вывода Vite. По умолчанию это `http://127.0.0.1:5173`; занятый порт меняется автоматически.
В Windows при ограничении выполнения `npm.ps1` используйте `npm.cmd` вместо `npm`.
Без make можно выполнить `go run ./cmd/server`; в отличие от `make run`, эта команда не читает `.env` автоматически.
Если установленный через MSYS2 Go не находит GOROOT, в PowerShell задайте `$env:GOROOT='C:\msys64\ucrt64\lib\go'`.

По умолчанию запросы идут по относительным путям `/api/scenario`, `/api/simulate`, `/api/explain`, `/api/recommend`, `/api/autopilot`.
`web/vite.config.ts` проксирует `/api` на Go в разработке. CORS для этого не нужен.
Для другого origin можно задать `VITE_API_BASE_URL=http://localhost:8081` в `web/.env.local` и перезапустить Vite. Go должен разрешить origin интерфейса через `CORS_ORIGIN`. В production значение встраивается при сборке. API-ключи остаются на сервере: переменные `VITE_*` публичны.

```sh
npm run build
```

Команда проверяет TypeScript и создаёт `web/dist`. Для production раздайте `dist` и проксируйте `/api` в Go на том же origin.
Go самостоятельно статические файлы frontend не раздаёт. `node_modules/`, `dist/`, `*.tsbuildinfo` и `.env.local` исключены через `web/.gitignore`.

## AI-автопилот: от одной цели до готового плана

На главной странице нажмите «Поручить план AI» или откройте «AI-автопилот» в навигации. Опишите цель обычным языком; при пустом поле сервер выбирает максимизацию Score в пределах бюджета. Пять решений вручную выбирать не требуется.

1. `POST /api/autopilot` с `{"goal":"Помочь Нуре и уложиться в 90 единиц"}` создаёт запуск и возвращает `202` с его ID.
2. Интерфейс опрашивает `GET /api/autopilot/{id}` через секунду после каждого ответа, пока статус `queued` или `running`. Показаны четыре AI-роли: координатор, аудитор цели, планировщик и проверяющий; отдельно — поиск Go, итерации, компромиссы и оценка расходов AI.
3. Только `completed` с полным результатом симуляции, `review.approved=true`, обратной связью и объяснением может автоматически заполнить решения. Перед применением интерфейс заново загружает каталог, сверяет его со снимком на старте и проверяет соответствие результата каталогу.
4. Проверенный результат и метаданные агентов сохраняются в истории, открывается экран результата. Дополнительный `/api/explain` не вызывается: используется объяснение из запуска.
5. Если во время работы изменены решения или название черновика, готовый план сохраняется отдельно в истории, не заменяя черновик. Его можно открыть и явно выбрать «Изменить решения».

«Остановить запуск» отправляет `POST /api/autopilot/{id}/cancel`. Даже если завершение опередит остановку, вариант не применяется автоматически. Навигация не прерывает серверную работу. ID, исходный каталог и отпечаток черновика хранятся в `localStorage['akim.autopilot.active.v1']`, поэтому после перезагрузки опрос возобновляется без нового платного POST.

Статусы `needs_clarification`, `infeasible`, `needs_review`, `budget_exceeded`, `unavailable`, `cancelled`, `timeout`, `failed` отображаются явно. Если такой ответ содержит промежуточный `result`, он не считается одобренным, не заменяет решения и не попадает в историю успешных планов. При `needs_clarification` уточнение показано рядом с целью; измените её и начните новый запуск. При сетевой ошибке опрос можно повторить; повтор не создаёт новый запуск. `429` означает занятый сервис, `503` — недоступный/отключённый автопилот, `404` — утраченный или истёкший ID.

Расходы AI в USD и бюджет города — разные величины. Интерфейс показывает серверную оценку стоимости, лимит, токены и признак неопределённой стоимости; бухгалтерский итог определяет провайдер. В mock-режиме платные запросы и автопилот отключены.

## Результат, оптимальность и проверка цели

Экран результата сначала показывает Score, его изменение, бюджет и критические показатели. Score измеряется в **баллах модели**, а не в процентах качества жизни. Он не нормализуется до «100% успеха». Ход работы агентов у завершённого запуска свёрнут и раскрывается по нажатию; во время работы события открыты. Стоимость и итог проверки остаются видимыми.

Если сервер передал необязательный `run.optimality`, интерфейс показывает `best_value`, `selected_value` и `gap` с единицами соответствующей цели:

- `score` — Score города, баллы;
- `weakest_district` — Score самого слабого района, баллы;
- `focus_district` — Score приоритетного района, баллы;
- `critical_first` — количество критических показателей: меньше лучше; `gap` означает лишние критические показатели выбранного плана относительно лучшего найденного.

Только `proven=true` вместе с `exhaustive=true` подтверждает лучший результат **для формализованной цели координатора, её ограничений и фиксированного синтетического датасета**. Это математическое свидетельство поиска, а соответствие исходному запросу отдельно проверяет reviewer. Одобрение reviewer и числовая оптимальность показаны раздельно. При `proven=false` интерфейс не называет план оптимальным. `score_ceiling` отображается только для цели `score` после полного перебора; он относится к заданным ограничениям.

В старых сохранённых запусках `optimality` может отсутствовать: они продолжают открываться, но доказательство или потолок Score не добавляются. Необязательное `review.revision_target` показывает направление доработки: `planner` — планировщик, `master` — координатор, `none` — направление не требуется.

Необязательное поле `goal_audit` имеет ту же структуру, что `brief`: `goal`, `summary`, `clarification`. Оно содержит независимую интерпретацию исходного запроса аудитором, который не видит интерпретацию координатора. Интерфейс показывает её отдельным блоком «Независимый разбор цели» и подписывает события роли `auditor` как «Аудитор цели». Наличие `goal_audit` само по себе не означает согласие агентов: согласование отражается событием `goal_agreed`, финальное одобрение остаётся отдельным решением проверяющего. Старые записи без этого поля продолжают открываться.

## Каталог и план

- Обзор районов загружается из `GET /api/scenario`, включая все 14 мероприятий, их точные названия, стоимость, лаги и эффекты.
- Каталог фильтруется по пяти направлениям. Район выбирается явно; у городских M2, M6, M12, M14 поле `district_id` в запросе полностью отсутствует.
- Панель содержит пять слотов, замену/удаление решения, смену района и серверный бюджет.
- Локальные правила каталога дают быстрые подсказки у действий: ровно пять уникальных мер, бюджет до 100, не больше двух мер направления, несовместимости M1/M3 глобально и M4/M7, M5/M13 в одном районе.
- **Общая стоимость, остаток и подтверждённая валидность отображаются только из ответа Go.** После изменения черновика с задержкой 250 мс отправляется `/api/simulate`. Неполный набор получает штатный 422 с бюджетом и `validation_errors`; полный допустимый — 200. Score этой фоновой проверки не показывается и в историю не сохраняется.
- Во время проверки/ошибки прежние бюджет и валидность скрываются. Устаревшие запросы отменяются. Кнопка запуска ждёт подтверждения Go. Ошибка позволяет повторить проверку, не теряя план.
- При запуске каталог проверяется заново. Изменившийся каталог требует повторного просмотра плана.

## Результат и объяснение

Явный запуск отправляет `/api/simulate`, сохраняет Result и затем отдельно запрашивает `/api/explain` с тем же планом.
Повторный запуск во время запроса блокируется. Ошибка сохраняет решения; ошибка explain сохраняет уже доступный расчёт.

Score, его разница, стоимость, итоговые значения всех районов, фактические дельты, реализованные эффекты и синергии берутся из ответа Go.
Полный эффект каталога отделён от реализованного эффекта `applied_effects`, который дан до clipping. Фактические изменения берутся из `indicator_deltas`.
Формула Score во frontend отсутствует.

При 422 используются `validation_errors`; русский текст выбирается по `code`, а не английскому `message`. Связанные `measure_ids` сохраняются.
`explanation.text` выводится React как обычный текст. HTML не интерпретируется.
`source=llm` обозначен как AI-объяснение, `fallback` — как резервное объяснение без AI.
Отдельных полей рекомендаций в `/api/explain` нет. Frontend не дописывает отсутствующие разделы.

Изменение решений скрывает предыдущий текущий результат, сохраняя его в истории.
Если `/api/explain` вернёт другой Result, его текст не прикрепляется к старому расчёту.

## Рекомендация оптимизатора

На экране решений есть «Показать лучший план»: `POST /api/recommend` с телом `{"mode":"best"}` **без поля decisions**.

- При `503` и `validation_errors[].code=not_ready` показывается **«Считается…»**, запрос повторяется через две секунды.
- Первые примерно 15 секунд после старта Go — лишь ориентир; ожидание продолжается до готовности, его можно отменить.
- Смена страницы отменяет запрос и повторения. Другие ошибки 503 не повторяются автоматически; показывается ошибка и ручной повтор.
- Score, стоимость, остаток, критические значения и пять решений рекомендации берутся из `best`.
- Кнопка «Заменить текущий план рекомендацией» явно заменяет все пять решений. Полный результат и AI загружаются обычным запуском.

`mode=improve` пока не подключён к интерфейсу. Рекомендация — результат оптимизатора Go, а не AI.

## Mock без backend

Скопируйте `.env.example` в `.env.local` и задайте `VITE_MOCK_MODE=true`, либо включите «Режим разработки» в шапке.
При ошибке каталога есть отдельная кнопка «Открыть mock без расчёта». Автоматического переключения нет.

Постоянная метка **MOCK** объясняет ограничение. `src/mock-scenario.json` — снимок реального `/api/scenario`, сверяемый тестом с Go.
Можно собирать и сохранять план. Общая стоимость и валидность не подтверждаются; симуляция, объяснение и оптимизатор отключены.
Фиксированного ответа для произвольного сценария нет. Файлы `tests/fixtures` не входят в приложение.

## Сохранение и сравнение

Черновик в `akim.draft.v1` восстанавливается из localStorage и проверяется по актуальному каталогу и сервером.
Повреждённые данные не ломают приложение; устаревшие меры/районы можно явно исправить.

Успешные запуски сохраняются в `akim.history.v1`: название, дата, план, полный ответ Go, объяснение и снимок исходного каталога.
Два результата сравниваются по серверным Score, районам и критическим показателям. Новые Score не рассчитываются.
Разные снимки данных сопровождаются предупреждением о несопоставимости. Даже одинаковые снимки не подтверждают одинаковую версию движка: API её не передаёт.
Удаление каждой записи подписано, последнее удаление можно отменить в текущей сессии.
История локальна для текущего браузера/origin; нет облака и синхронизации вкладок. Ошибка/квота localStorage показывается пользователю.

## Проверки

```sh
npm test
npm run test:api
npm run test:integration
npm run build
```

- `npm test`: Vitest + Testing Library в jsdom, без сервера. Валидация, хранение, API, выбор решений, клавиатура в DOM, серверная проверка бюджета, отмена старых запросов и цикл `503 not_ready → 200`. Автопилот проверяется через имитацию HTTP: одна цель → проверенный результат, доработка после замечаний, частичные результаты, лимит расходов, гонка остановки/завершения, восстановление ID, изменения черновика/каталога и mock без платных запросов.
- `npm run test:api`: нужен живой Go. Проверяет каталог, документированный пример, ограничения, все несовместимости, параллельные запросы и лучший план, сверяя его с `/api/simulate`. Ожидание оптимизатора ограничено 120 секундами в тесте.
- `npm run test:integration`: реальное React-приложение в jsdom с HTTP-запросами в Go. Сервер запускайте без AI-ключа: тест проверяет fallback, выбор пяти мер, серверный бюджет, результат и восстановление после повторного открытия.
- Для HTTP-тестов другой адрес задаётся через `API_URL`; это настройка тестового процесса, не приложения.

Последняя проверка frontend: **94 теста в 8 файлах прошли** за 14,46 секунды, TypeScript и production-сборка Vite прошли. Новые тесты проверяют доказательство и его отсутствие, неверные значения контракта, критические показатели как количество, нулевую разницу без доказательства, совместимость истории, сворачивание хода агентов, порядок результата перед деталями и необязательный независимый аудит цели.

Документированный план: M7/Нура, M8/Нура, M10/Нура, M12/город, M5/Сарыарка.
Реальный Go ответ: стоимость **95**, остаток **5**, Score после **56.54306999999999**, отображение **56,54**, критические значения **2 → 0**.
Оптимизатор при проверке вернул стоимость **98**, Score **57.236734999999996**. Числа не подставляются в приложение.

## Выполненная проверка и её ограничения

Проверены три первоначальных запуска с OpenAI во встроенном desktop-браузере при размере **1265×712**. После добавления протокола исправлений выполнен ещё один живой запуск: Score **57.236735**, стоимость **98**, критические показатели **0**, подтверждённый оптимум и нулевое отставание показаны в интерфейсе. Ключ не попадает во frontend. Отображение доказательства проверено также DOM-тестами и сборкой; подробности проверки исправления бюджета — в [docs/autopilot.md](../docs/autopilot.md).

После добавления четвёртого агента выполнен backend-тест `TestLiveAuditorCorrection` с реальным OpenAI: **38,37 секунды, 2 итерации, 5 реальных API-вызовов**, итоговый Score **57.236735**, бюджет города **98**, критические показатели **0**, оценка расходов AI **$0.009695**. Первый ошибочный ответ координатора был искусственно подставлен без API-вызова: в нём отсутствовало ограничение `max_critical=0`. Независимый аудитор обнаружил расхождение, после чего цель была исправлена. Это проверка восстановления backend после внесённой ошибки; браузерная проверка нового аудита этим тестом не заменяется. Подробности — в [docs/autopilot.md](../docs/autopilot.md).

Контрольные размеры 390/768/1440 px, видимость фокуса на устройствах, системный reduced motion и touch пока визуально не проверены. Клавиатурный путь проверен в DOM; это не замена браузеру. Настоящий fallback без ключа также проверен.
Production reverse proxy, реальные мобильные устройства, quota браузера и многовкладочная синхронизация не проверены.
Все данные синтетические; оригинальная иллюстрация Астаны не является картой районов. Игрового таймера и случайных городских событий нет.

[Ранний отчёт перед демонстрацией](DEMO-CHECK.md) относится к версии до автопилота; актуальная проверка AI и frontend описана выше. В текущей ветке сервер раздаёт API, а сайт запускается или размещается отдельно согласно разделу «Запуск».
